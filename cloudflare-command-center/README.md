# Superior Maintenance and Remodeling Command Center

This Cloudflare Worker uses D1 for durable estimates, invoices, customer details, and customer feedback. The responsive black, gold, and silver dashboard is at `/owner`. Customer approval and decline pages use private `/review/<token>` links.

## Deployment from main

GitHub Actions in `.github/workflows/deploy-superior-cloudflare.yml` deploys **main**. The legacy migration branch no longer triggers the production workflow.

1. A separate validation job installs the pinned development tools, builds public assets, runs SQLite-backed Worker tests and mobile/desktop browser checks, and validates the Wrangler bundle.
2. The deployment job explicitly selects the existing **GitHub Actions environment** named `CLOUDFLARE_API_TOKEN`. Its environment secret `CLOUDFLARE_API_TOKEN` overrides a repository secret of the same name. A format-only scope check confirmed that the environment value is usable while the old repository value is a setting-name placeholder. Actual permissions are verified by the deployment commands.
3. The workflow rejects a setting name, pasted command/header, or whitespace instead of silently rewriting the credential. The token is never printed or written into source.
4. A Worker settings check reports only the presence and binding type of required settings. It never prints their values. Wrangler applies pending additive D1 migrations, then deploys the Worker and allowlisted public assets. A denied migration is reported; deployment can still proceed against an existing schema, but the live readiness check must pass.
5. A read-only live check verifies the actual Wrangler-reported website URL, public pages, D1 schema readiness, and owner access protection. The URL is written to the successful run's summary only after these checks pass.

The Worker is `superior-command-center`. Its D1 binding is `DB`, database name `superior-command-center`, and configured database ID is `4feb6f63-1102-467a-87e6-256309364f12`. Do not create a replacement database or change this ID when preserving existing business records.

### Required secrets

- **GitHub environment secret `CLOUDFLARE_API_TOKEN` inside environment `CLOUDFLARE_API_TOKEN`:** the raw token value generated by Cloudflare. Keep the secret's Name unchanged and put only the actual token in the Secret field. Scope the token to the Superior account with Workers Scripts: Edit and D1: Edit permissions. A token label, token ID, variable name, or full curl command is not the credential.
- **Cloudflare Worker secret `OWNER_PASSWORD`:** the private owner sign-in password.
- **Cloudflare Worker secret `SESSION_SECRET`:** a private random signing secret with at least 32 bytes of entropy.

Configure Worker secrets in Cloudflare or with `npx wrangler secret put OWNER_PASSWORD` and `npx wrangler secret put SESSION_SECRET`. Retain existing values; redeployments must not rotate them automatically. Do not paste credentials in chat or commit them, `.dev.vars`, `.env` files, invoices, or private backups.

In Cloudflare, open **Workers & Pages → superior-command-center → Settings → Variables and Secrets**. Add `OWNER_PASSWORD` and `SESSION_SECRET` with type **Secret**, not Text. Use a new private owner password if a previous value appeared in public deployment logs. The settings check blocks a deployment that would expose either setting as plaintext. `keep_vars: true` preserves dashboard-managed variables; secrets remain managed in Cloudflare and are not embedded in the Wrangler configuration.

A deployment blocked by the token check is not a live success. Correct the secret inside environment `CLOUDFLARE_API_TOKEN` at https://github.com/superiormandr-star/Fieldnotes/settings/environments and rerun the latest main workflow. GitHub cannot reveal the saved token value; an invalid token must be replaced securely at that page.

## Business workflow

- Create and edit itemized estimates with tax, customer contact information, project details, and notes.
- Generate a private approval/decline link and copy it or open an email draft. The website does not send email automatically.
- Approval atomically creates one saved invoice. Repeated or concurrent customer decisions do not create duplicate invoices.
- View invoice customer details and payment status. Recording payment preserves the original payment date on retries.
- Customers can leave one 1–5 rating and comment after deciding on an estimate. Feedback is tied to the private customer link and visible to the owner.
- D1 records persist across Worker deployments. Owner APIs require authentication.

## Preserve and import records

Download private backups from `/owner/backup`. Exports include estimates in every status, invoices, and customer feedback. Keep independent copies in private storage.

Imports are **additive**: existing records, paid invoices, and feedback are retained, conflicts are skipped, and imported/skipped counts are shown. Legacy backups without feedback remain supported. Files are limited to 250 total records per import; larger backups require staged imports. No migration or import deletes existing business records.

The older Node/Render server is a separate fallback runtime. Shared frontend assets disable unsupported feedback and unsafe legacy restore until the server advertises the required capabilities. Export old records before changing any old hosting service; this deployment does not shut it down or import private data automatically. Old approval links need the new Cloudflare origin when moving between hosts.

## Automatic Drive and email backups

Saving a new estimate atomically queues its backup alongside the D1 record. Customer approval queues the resulting invoice, and recording payment queues its updated state. The Worker starts delivery after the save; a scheduled catch-up runs every 15 minutes for pending deliveries. It does not generate a separate daily email. A Google outage cannot remove the saved document or its queued backup.

Each delivery includes one complete, restore-compatible JSON snapshot of all estimate statuses, invoices and customer feedback. The same file is saved to the existing private **Superior Command Center — Private Backups** folder and attached to an email sent to **superiormandr@gmail.com**. Delivery receipts remain in D1. Repeated processing does not duplicate completed deliveries; an uncertain Gmail outcome requires checking Gmail and is never blindly resent. Drive and email timestamps show confirmed delivery separately. A complete-backup timestamp is recorded only when both destinations confirm success.

### Connect the business Google account

The app needs its own Google authorization. Google Drive and Gmail connected to ChatGPT do not authorize this separate Cloudflare Worker.

1. Reuse the existing Google OAuth web client if one is already available. Enable the Google Drive API and Gmail API for its Google Cloud project. Register this exact authorized redirect URI: `https://superior-command-center.superiormandr.workers.dev/api/google/callback`.
2. In Cloudflare **Workers & Pages → superior-command-center → Settings → Variables and Secrets**, securely configure `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`. The client secret must use type **Secret**. Keep the existing `OWNER_PASSWORD` and `SESSION_SECRET`; do not paste any secret into chat or commit it to the repository.
3. Sign in to the Command Center, open **Backup & restore**, select **Connect Drive & email**, and authorize the selected business Google account. Google approval grants access to the existing private backup folder and permits sending backup attachments to the same business Gmail. The app validates the account and private folder before retaining encrypted offline authorization in D1.
4. Confirm the first backup reports both Drive and email delivery. The existing folder and Gmail attachment are independent recoverable copies. Until authorization and delivery succeed, the page reports pending setup and manual downloads remain available.

The destination is configured by the nonsecret `BACKUP_EMAIL` and `GOOGLE_DRIVE_BACKUP_FOLDER_ID` Wrangler values. Runtime operations are restricted to that recipient and folder; they never change folder sharing or delete existing backups. A publicly shared destination is rejected. OAuth refresh tokens are encrypted using the existing session secret and persist across deployments. Changing that secret requires reconnecting Google.

For unattended use, check the Google OAuth application's publishing status: Google can expire offline tokens issued by an app left in **Testing** after seven days. Provider revocation or expiration is reported on the backup page and requires reconnecting. Automatic delivery is limited to complete JSON files up to 8 MB; larger datasets require a manual export and staged recovery. Existing imports remain additive and limited to 250 records per request.

## Local checks

Use Node 24:

```bash
cd cloudflare-command-center
npm install
npm run build
npm test
npm run test:browser
npx wrangler deploy --dry-run
```

Browser tests use installed Chrome/Chromium or a Playwright browser; `CHROME_PATH` can select an existing browser. All tests use isolated synthetic records and temporary SQLite storage. They do not access production customer records.

`GET /api/health` is a read-only readiness check for the D1 binding, required schema, and owner-secret presence. It does not disclose business records or secret values. Live deployment checks read this endpoint and verify that anonymous requests cannot read estimates, invoices, or feedback.

The build copies only allowlisted website assets. It excludes the Node server, Google credentials, private backups, and test data.




### Production deployment source

Use `.github/workflows/deploy-superior-cloudflare.yml` as the production deployment pipeline. Cloudflare Workers Builds automatic builds must stay disabled for this Worker. A duplicate build connection rooted at the repository root deployed static-only versions and stripped runtime bindings. The Actions preflight now rejects duplicate auto-builds and missing required bindings before uploading.

Worker rollback changes the active version, but secret inheritance uses the latest uploaded version. After an accidental static-only upload, restoring an older deployment alone does not repair the next upload's inherited secrets. Recover existing bindings through version references; never rotate `SESSION_SECRET` during recovery because persisted provider refresh tokens are encrypted with it. Keep the existing D1 database binding and apply only additive migrations.

The production OneDrive inspection reports binding presence, encrypted-token-envelope presence, and the last confirmed upload timestamp. This is separate from basic website/D1 readiness. A successful deployment does not establish Microsoft consent or automatic backup delivery.

## PayPal invoice checkout

Approved estimates expose their generated invoice and payment status at the existing private customer review link. `POST /api/review/<token>/payment/create` creates an Orders v2 checkout for the saved USD invoice total; `/payment/capture` retrieves the associated order and verifies a completed full capture, invoice identity, currency, and merchant before recording payment and queuing its backup. Retried requests reuse the saved order and stable request IDs. Client-supplied amounts, order IDs, and paid flags are ignored. This adds no migrations or replacement databases. Branding assets are unchanged.

Checkout stays unavailable until all four Worker settings are configured: `PAYPAL_MODE` (`sandbox` first), `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET` (Secret), and `PAYPAL_MERCHANT_ID`. Never commit credentials. Verify a real sandbox purchase, return, cancellation, retry, and merchant receipt before configuring live settings. Automated tests mock PayPal and do not prove merchant authorization or live settlement. Subscription plans in the separate marketplace are unrelated; this integration does not create or activate recurring plans. Standalone invoices have a private payment link generated by the owner through Get payment link; the same capture checks apply. Refunds, disputes and asynchronous webhook reconciliation are not implemented.

Customer feedback remains private to the owner; no public review is invented or published. Public estimate inquiries still open the customer's email app and require the customer to send the draft.
